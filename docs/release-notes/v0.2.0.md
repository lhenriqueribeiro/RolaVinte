# v0.2.0 - Fundação técnica: lint de arquitetura, CI e harness de contrato (2026-08-09)

Resumo: esta versão não adiciona funcionalidade de produto — ela transforma os guardrails de
`.claude/rules/` em verificação automática. As fronteiras entre camadas passam a quebrar o lint, a API
ganhou um harness de testes de contrato que sobe o Fastify com adaptadores em memória (sem Supabase e sem
rede), e existe um workflow de CI que roda `check`, `test` e `build`. Junto veio a correção de um
bloqueador de ambiente: até agora nada no repositório lia `apps/api/.env`, então a API não subia mesmo com
o arquivo preenchido.

## Entregas

### RV-001 — ESLint + Prettier + lint de arquitetura

ESLint 10 em flat config na raiz (`eslint.config.js`), com typescript-eslint, `eslint-plugin-react-hooks`
e Prettier. As cinco fronteiras da tabela do card foram codificadas em `no-restricted-imports` por
diretório, bloqueando tanto pacotes (`fastify`, `@supabase/*`, `resend`, `socket.io`) quanto caminhos
relativos e com alias (`../infra/**`, `@/lib/socket`). Além da tabela, `config/` também está barrado em
`dominio/` e `aplicacao/` (só `config/env.ts` lê `process.env`), e `components/ui` não pode importar
`features/**` nem `socket.io-client`. `apps/api/src/app.ts` e `main.ts` ficam fora dos overrides de camada
por serem o composition root.

Por que importa: a regra de dependência deixou de depender de revisão humana. E não é só configuração — as
regras com informação de tipo (`no-floating-promises`, `no-misused-promises`, família `no-unsafe-*`)
acharam dois bugs reais, corrigidos nesta versão:

- `apresentacao/ws/gateway-jogo.ts`: o middleware `io.use()` era `async`. O Socket.IO ignora a promessa
  devolvida, então uma rejeição em `servicoToken.verificar` nunca chamaria `next()` e deixaria o handshake
  do cliente pendurado, sem erro nem timeout de aplicação. Agora `autenticarHandshake` encerra no `then` e
  no `catch`, e `socket.handshake.auth?.token` é tipado como `unknown`.
- `apresentacao/http/autenticacao.ts`: `criarAutenticador` devolvia função `async` anotada como
  `preHandlerHookHandler` (assinatura de callback com `done`). Trocado por `preHandlerAsyncHookHandler`
  nos 5 arquivos que declaravam o tipo.
- `apps/web/.../PaginaConvite.tsx`: `onSuccess` do TanStack Query devolvia a promessa de `navigate()`, que
  espera retorno `void`.

Uma regra foi relaxada com justificativa em comentário no `eslint.config.js`:
`@typescript-eslint/no-unnecessary-type-assertion` está desligada. Como o client do Supabase é `any`, o
autofix dela removia as asserções `data as RowX` dos repositórios — apagando a única tipagem da fronteira
com o banco e disparando `no-unsafe-argument` em cascata.

O Prettier rodou uma vez no repositório (47 arquivos reformatados, `printWidth: 100`, aspas simples).
Markdown e `apps/api/supabase/migrations/` estão no `.prettierignore`.

Testes: `apps/api/src/testes/fronteiras-arquitetura.test.ts` (16 casos) grava fixtures temporários com
imports proibidos, roda o ESLint via API Node e exige que a regra acuse — mais um caso negativo
(`aplicacao` importando `dominio` não pode ser acusada). Assim ninguém afrouxa o `eslint.config.js` sem
ficar vermelho.

### RV-002 — Pipeline de CI

`.github/workflows/ci.yml`, disparando em `push` e `pull_request`, com Node 22 e cache de npm via
`actions/setup-node`. Instalação com `npm ci` (o repositório versiona `package-lock.json`) e execução em
sequência de `npm run check`, `npm run test` e `npm run build`. Sem segredos: nenhum dos três comandos
precisa de `.env` ou rede, porque a API não sobe no CI. Também tem `concurrency` com cancelamento de runs
antigos do mesmo branch, `permissions: contents: read` e `timeout-minutes: 15`.

Não há passo separado de eslint: o lint entra pelo `check` da raiz, que agora é `lint && typecheck`.

Por que importa: é o gate que impede main quebrada. Ver "Limitações conhecidas" — hoje ele ainda não
executa.

### RV-003 — Harness de testes de contrato HTTP

A montagem HTTP saiu do composition root para `apps/api/src/app.ts`, em duas funções (`criarServidorHttp` e
`registrarRotas`), o que evita o ciclo Fastify → Socket.IO → PublicadorSocket → casos de uso. `main.ts`
ficou com env, composição da infra real, registro das rotas, gateway e `listen` — sem mudança de
comportamento em produção.

Foram criados fakes em memória fiéis a todas as ports: repositórios (usuário, mesa, personagem, cena,
mensagem), `ServicoEmail` com caixa de saída inspecionável, `PublicadorEventosMesa`, `GeradorId`
determinístico com UUID v4 válido, `Relogio` fixo, `ServicoSenha` e `ServicoToken`. Os fakes guardam
instantâneos e reconstituem a entidade a cada leitura (como o adapter Supabase faria), então mutação sem
`salvar` não vaza para o "banco" — a substituição pelo Supabase continua honesta (Liskov). Os fakes de
mesa e personagem recebem `UsuarioRepository` por construtor porque os read models incluem nome do
mestre/dono.

`criarAppDeTeste()` (`apps/api/src/testes/harness.ts`) devolve `app`, `fakes`, `autenticarComo`,
`aguardarEventos` e `encerrar`. O `aguardarEventos` existe porque o `EventBusMemoria` despacha assinantes
de forma assíncrona — é necessário antes de ler o email de convite no fake. O harness usa o
`JwtServicoToken` real com segredo fixo em código (nada de `process.env`), para que o preHandler seja de
fato exercitado; a senha usa `FakeServicoSenha` porque bcrypt real deixaria a suíte lenta.

17 testes de contrato via `app.inject`:

- `rotas-auth.test.ts` (7): registro 201 com JWT de 3 partes; email duplicado 409 sem criar segundo
  usuário; payload inválido 400; login 200 com token que abre `GET /api/auth/eu`; senha errada 403;
  `GET /api/auth/eu` sem header 401 com `{ erro: "Autenticação necessária." }`; token forjado 401.
- `rotas-mesas.test.ts` (7): `GET /api/mesas` sem header 401; criação 201 com `meuPapel` mestre e
  `mestreNome` resolvido pelo read model; nome curto 400; listagem só com as mesas do solicitante; abrir
  mesa de terceiro 403; mesa inexistente 404; fluxo convidar → extrair o token do email capturado pelo
  fake → aceitar → jogador tentando convidar recebe 403.
- `servidor-http.test.ts` (3): `GET /api/saude`, cabeçalho CORS da origem do front e 404 em rota
  desconhecida — guardas do wiring que o refactor tocou.

Duas decisões que fogem da letra do card, de propósito: a rota de saúde foi declarada em
`criarServidorHttp` com o caminho completo `/api/saude` (é onde ela já vivia, e é o que RV-004 cita), e
nenhum `setErrorHandler` global foi adicionado — isso é escopo explícito do RV-005 e mexer nele agora
mudaria o corpo de erro em produção.

### Correção fora de card: a API não carregava o `.env`

`config/env.ts` é o único ponto que lê `process.env` e faz fail-fast, mas nada no repositório alimentava
`process.env` a partir de `apps/api/.env` — não havia `dotenv` nem flag `--env-file`. Seguir a instrução do
CLAUDE.md ("copie `.env.example` para `apps/api/.env`") não fazia a API subir: ela abortava reclamando de
`JWT_SEGREDO`/`SUPABASE_URL`. Os scripts `dev` e `start` da API passaram a usar
`--env-file-if-exists=.env`, e `engines.node` da raiz subiu de `>=22` para `>=22.9`, versão mínima que
suporta a flag.

## Qualidade

Resultado real da verificação desta versão:

| Comando | Resultado |
|---|---|
| `npm run check` | verde — lint sem nenhuma mensagem + `tsc --noEmit` nos 3 workspaces |
| `npm run test` | verde — 55 testes (12 em `@rolavinte/shared`, 43 em `@rolavinte/api`) |
| `npm run build` | verde — inclui o `vite build` do web |
| `npx prettier --check .` | "All matched files use Prettier code style!" |

Os 43 testes da API estão em 6 arquivos: domínio, use case com fakes, 3 de contrato HTTP via `inject` e os
16 casos de fronteira de arquitetura que rodam o ESLint de verdade. Os 12 do shared cobrem o motor de
dados. Auditoria manual confirmou zero imports de `supabase`/`fastify`/`resend`/`socket.io` em
`apps/api/src/dominio` e `apps/api/src/aplicacao`, `main.ts` com a ordem de composição correta e o `check`
da raiz agregando o lint antes do typecheck.

## Para quem já tem o projeto clonado

1. `npm install` na raiz — há devDependencies novas (`eslint`, `@eslint/js`, `typescript-eslint`,
   `eslint-plugin-react-hooks`, `eslint-config-prettier`, `prettier`, `globals`), e `eslint` também entrou
   em `apps/api` porque o teste de fronteiras o importa como biblioteca.
2. Confira sua versão do Node: o mínimo agora é **22.9** (`engines.node`), por causa da flag
   `--env-file-if-exists` usada nos scripts `dev`/`start` da API.
3. Se você já tinha `apps/api/.env`, ele passa a ser lido automaticamente por `npm run dev`. Se você
   contornava o problema exportando variáveis no shell, isso continua funcionando (o shell tem
   precedência sobre o arquivo).
4. `npm run check` agora roda `lint && typecheck` — pode falhar em código local que passava antes.
   Comandos novos: `npm run lint`, `npm run lint:fix`, `npm run format`, `npm run format:check`.
5. O Prettier reformatou 47 arquivos. Branch antigo em cima desta base tende a dar conflito cosmético:
   rode `npm run format` no seu branch antes do merge para reduzir o ruído.

## Limitações conhecidas

- **O diretório não é um repositório git** (não existe `.git`). O workflow de CI está correto, mas é
  código morto até haver `git init`, commit do `package-lock.json` (existe em disco, 217 KB, não
  versionado) e um remote no GitHub. Não foi feito `git init` por ser decisão do usuário. Consequência
  direta: nenhum dos gates desta versão está rodando de fato em nenhum lugar além da máquina local.
- **`npm run build` não emite JavaScript** para `@rolavinte/shared` e `@rolavinte/api` — os dois scripts
  são `tsc --noEmit`. Só o web gera artefato (`dist/`, 408 KB de JS). Na prática o passo "Build de
  produção" do CI é um segundo typecheck do backend, e o deploy da API hoje dependeria de
  `tsx src/main.ts`. Relevante para os cards de operação (E13).
- **`apps/web` não tem script `test` nem runner.** `npm run test --workspaces --if-present` pula o
  frontend em silêncio, inclusive no CI, o que dá falsa sensação de suíte verde. Hooks, stores Zustand e a
  integração socket → cache do TanStack Query não têm cobertura nenhuma.
- **`format:check` não está no `check` nem no CI.** A base está 100% formatada hoje, mas uma divergência
  futura não quebra o pipeline. Ficou de fora de propósito: acoplar formatação ao gate criaria falha de
  build por diff cosmético.
- **Boot end-to-end da API não foi validado**, por não haver credenciais Supabase reais no ambiente. A
  composição do `main.ts` foi verificada por leitura de código, mais um teste isolado de carregamento de
  env (com um `.env` temporário criado e removido durante a verificação).
- **Rows do Supabase atravessam a fronteira como `any`.** Sem tipos gerados do schema, a única tipagem são
  asserções manuais (`data as RowMesa`). Renomear uma coluna numa migration não gera erro de compilação em
  lugar nenhum — o mapper quebra só em runtime. É também o motivo de
  `no-unnecessary-type-assertion` estar desligada. Candidato a card: gerar `Database` types e parametrizar
  `createClient<Database>`.
- **`request.usuarioId` é tipado como sempre presente** (`declaration merging` em
  `apresentacao/http/autenticacao.ts`). Uma rota nova registrada sem o preHandler `autenticar` compila
  normalmente e entrega `undefined` ao caso de uso — a autorização falharia por comparação com `undefined`
  em vez de estourar. Um tipo `usuarioId?: string` com helper `exigirUsuario(request)` tornaria o
  esquecimento erro de compilação.
- **O harness duplica o composition root.** `testes/harness.ts` replica a montagem dos 20 casos de uso
  feita em `main.ts`. É a escolha certa para não tocar em Supabase/Socket.IO nos testes, mas há risco de
  deriva: uma rota nova registrada só em `main.ts` não passa a ser exercitada pelos testes de contrato, e
  nada acusa.
